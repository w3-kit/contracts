# Token Vesting

## What is the Vesting Program?

The Vesting program allows an authority to lock SPL tokens in a vault and release them to a beneficiary over time using a linear schedule with an optional cliff. This is the Solana equivalent of OpenZeppelin's [VestingWallet](https://docs.openzeppelin.com/contracts/5.x/api/finance#VestingWallet) and [VestingWalletCliff](https://docs.openzeppelin.com/contracts/5.x/api/finance#VestingWalletCliff).

Common use cases:
- Employee token grants with cliff periods
- Investor token lockups
- Team allocation schedules
- Advisor vesting with revocability

## Core Mechanisms

### Linear Vesting with Cliff

The vesting formula is straightforward:

```
if now < start + cliff_duration:
    vested = 0
elif now >= start + duration:
    vested = total_deposited
else:
    vested = total_deposited * (now - start) / duration

releasable = vested - released_amount
```

The cliff acts as a gate: nothing vests until `cliff_duration` passes. After the cliff, vesting is calculated linearly from `start_time` (not from the cliff end). This means once the cliff passes, the beneficiary can immediately claim the portion that would have vested during the cliff period.

### Permissionless Release (OZ Semantics)

Unlike many Solana vesting implementations that require the beneficiary to sign, this program makes `release()` permissionless — anyone can crank it. Tokens always go to the beneficiary's token account regardless of who submits the transaction.

This matches OpenZeppelin's `VestingWallet.release()` which is a public function callable by anyone. Benefits:
- Bots can automate releases
- Third parties can sponsor gas
- No beneficiary key management required for claiming

The `has_one = beneficiary` constraint ensures tokens always flow to the correct destination.

### Multiple Schedules via `schedule_id`

The PDA is derived from: `"vesting" + authority + beneficiary + mint + schedule_id.to_le_bytes()`.

The `schedule_id` field allows an authority to create multiple concurrent vesting schedules for the same beneficiary and token. Without it, only one schedule per (authority, beneficiary, mint) triple would be possible.

### Revocability

Schedules can optionally be revocable. When revoked:
1. Already-vested (unreleased) tokens go to the beneficiary
2. Unvested tokens return to the authority
3. The schedule is permanently marked as revoked
4. No further `release()` or `deposit()` calls are allowed

## EVM vs. Solana: Key Differences

### Account Model

In EVM, `VestingWallet` is a standalone contract that *is* the vault — tokens are sent directly to the contract address. On Solana, the state (VestingSchedule PDA) and the vault (Token Account PDA) are separate accounts owned by the program.

```
EVM:  VestingWallet contract == vault
Solana: VestingSchedule PDA (state) + Vault PDA (tokens)
```

### Deposits

In EVM, anyone can transfer ERC-20 tokens to the VestingWallet address at any time — there's no explicit "deposit" function. On Solana, we have an explicit `deposit` instruction because the vault PDA's authority is the VestingSchedule PDA, requiring a CPI transfer.

### Clock

EVM uses `block.timestamp` which is set by validators. Solana uses the `Clock` sysvar which provides `unix_timestamp`. Both are approximate but sufficient for vesting durations measured in days/months.

## Security Considerations

### Revoked Schedule Guard

After revocation, both `release()` and `deposit()` check `schedule.revoked` and reject if true. Without this guard, time-based vesting math would continue to produce positive `releasable` values if tokens were sent to the vault post-revocation.

### Retroactive Deposit Semantics

Tokens deposited mid-schedule are immediately subject to the vesting formula. If 50% of the duration has elapsed and someone deposits 1,000 tokens, the formula treats 500 as already vested and immediately releasable.

This is identical to OZ's behavior (since ERC-20 transfers to the wallet are external) but is a critical UX footgun. **Operators should deposit the full grant amount at or before `start_time`.**

### Overflow Protection

All arithmetic uses `checked_add`, `checked_mul`, `checked_div` with `u128` intermediates for the vesting calculation. The formula `total_deposited * elapsed / duration` can overflow `u64` when `total_deposited * elapsed` exceeds 2^64, so we upcast to `u128` before multiplying.

### PDA as Vault Authority

The vault's token authority is the VestingSchedule PDA itself. This means only the program (via CPI with PDA seeds) can move tokens out of the vault. No external keypair can drain it.

### Permissionless Release Safety

The `release()` instruction is permissionless — any account can sign as `payer` and crank the release. Security is **not** enforced via signer checks on the beneficiary. Instead, it is guaranteed at the account-constraint level:

1. `has_one = beneficiary` ensures the beneficiary account passed matches the one stored in the schedule.
2. `beneficiary_token_account.owner == vesting_schedule.beneficiary` ensures the destination token account is actually owned by the beneficiary. An attacker cannot substitute their own token account because the owner field would not match.
3. `beneficiary_token_account.mint == vesting_schedule.mint` ensures the correct token type.

This combination makes it impossible for a third party to redirect released tokens to an account they control, even though they can submit the transaction.

## Instruction Walkthrough

### `initialize`

Creates the VestingSchedule PDA and Vault PDA. Validates:
- `start_time != 0`
- `duration > 0`
- `cliff_duration <= duration`

The `schedule_id` parameter is the first argument and is used in seed derivation.

### `deposit`

Transfers tokens from depositor to vault via CPI. Guards:
- `amount > 0`
- `!revoked`

### `release`

Calculates releasable amount, transfers from vault to beneficiary. Guards:
- `!revoked`
- `releasable > 0`

Permissionless — any signer can pay for the transaction.

### `revoke`

Splits vault balance between beneficiary (vested portion) and authority (unvested portion). Guards:
- `revocable == true`
- `!revoked`

## Testing

Tests use `solana-bankrun` with `setClock` for deterministic time control. This eliminates flaky tests caused by wall-clock drift on slow CI runners. Each test warps to an exact timestamp before calling time-sensitive instructions, enabling precise assertions (e.g., exactly 50% vested at midpoint).

```typescript
// Warp to exactly midpoint
await warpTo(ctx.context, startTime + 50);
// Assert exact vested amount
expect(balance).to.equal(500_000); // 1_000_000 * 50/100
```
